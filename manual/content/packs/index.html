    Packs¶

    A pack is one file (or a few) that holds a game's content: compressed with zstd, optionally encrypted with AES-256-GCM, and mounted in the file system like a folder. A shipped game's res:// is its packs; during development it is a folder. Mods are not packs: they stay folders or zips so that players can make them without tools.

    Making one¶

    ./build.sh pack Samples/Mods/res Bin/data/game.wpak                      # every file under the folder (Weft.Runtime --pack, with .env loaded)
./build.sh pack Content Bin/data/game.wpak --split-mb 1024 --level 15      # parts of about 1 GiB, a smaller (slower) compression
./build.sh pack Content Bin/data/patch.wpak --base Bin/data/game.wpak      # a patch pack

    ./build.sh pack runs Weft.Runtime --pack (the engine's host program has the content library and the native libraries, and the editor and the export step use the same PackWriter); the wrapper loads .env, so WEFT_PACK_KEY applies. Run Weft.Runtime --pack <folder> <out.wpak> yourself to pack without the wrapper. Paths in the pack are relative to the folder (packages/core/mod.wmod); files and folders whose name starts with a dot are left out; every name must be valid in a virtual path (no .., no nul…), and the tool says which are not. From code: GamePacker (below), or PackWriter (Add, AddFile, Remove, Finish) to write the files yourself.

    • Compression. Each file is compressed with zstd when it has 64 bytes or more and that saves at least 10%; the rest (PNG, KTX2, OGG…) is stored as it is. --level is zstd's 1 to 22 (default 12). Large files are compressed on several threads.
    • Splitting. A pack grows to --split-mb (default 1536) and then continues in the next part: game.wpak, game_001.wpak, game_002.wpak… A file is never split, so one that is bigger than the limit gets a part to itself. Opening the first part finds the others; a part that is missing is an error that says which.
    • Patch packs. With --base the packs you name (in order, with the same key) are what the game has already: the new pack holds only the files that are new or different, and a removal for each file that is gone. Mounted over the base, it replaces, adds and removes.

    With --cooked the pack is what a shipped game needs: the imported artifacts instead of the sources they replace and their .wimp files (Asset import), the authored documents (scenes and prefabs), the definitions of the base packages (the .xml files in the Content folders of packages/<id>/mod.wmod) and the UID list imported/assets.xml as cooked XML at the same paths, everything else as it is: mod.wmod, schemas, .rml documents, scripts and mods stay text. It needs the folder to be imported first. The summary line says how many documents were cooked (game.wpak: 14 files (5.5 MiB) in 1 part(s), 4.9 MiB, 2 cooked). Files under dev_mods/ are never cooked, and a scene or a definition file that is not well-formed XML is an error (exit code 1) that names its path. A script that read such a file as text with fs.read_text gets bytes from a cooked pack: it reads definitions with defs, scenes with world:load_scene_file and other XML with xml.load, which work on both forms (Tests/Fixtures/ShippedGame is packed --cooked and run from the pack by a test).

    From code: GamePacker¶

    Weft.Runtime --pack is a thin command over GamePacker in Weft.Content.Packs, which an export or a tool calls directly:

    PackReport report = GamePacker.Pack(new PackRequest
{
    Folder = "Content",                   // the game folder: it is res://
    Output = "build/data/game.wpak",      // the first part; more are game_001.wpak…
    Cooked = true,                        // artifacts instead of sources, cooked documents (needs an import first)
    AllowNothingImported = true,          // a game with nothing to import is packed as it is, not an error
    Key = PackKey.FromEnvironment(),      // the caller asks; the packer never reads the environment
    Exclude = ["dev_mods/", "data/"],     // folder-relative prefixes left out
    // Bases, SplitBytes (1536 MiB) and CompressionLevel (12) as for the options above
});
Console.WriteLine($"{report.Added} files, {report.CookedDocuments} cooked, {report.PackedBytes} bytes in {report.Parts.Count} part(s)");

IReadOnlyList<string> paths = GamePacker.PathsOf(request);   // what Pack would pack, without writing: for an export that lists or checks them

    Pack throws a ContentException when the folder is not a folder, when a cooked pack has nothing imported (unless AllowNothingImported), when a path cannot be in a pack, or when an authored document does not parse; and an IOException when writing fails. PackReport says how many files were added, left unchanged and removed (the last two for a patch pack), how many of the added files were cooked documents, the bytes before and after compression, and the part files. Packing the same folder twice gives the same files, so a patch pack over a cooked base holds only what changed.

    Using one¶

    PackKey? key = PackKey.FromEnvironment();                    // null when WEFT_PACK_KEY is not set
using var pack = PackSource.Open("data/game.wpak", key);     // the key is ignored for a pack that is not encrypted
files.Mount("res://", pack);                                  // later mounts override earlier ones: a patch pack goes after

    Weft.Runtime --game <folder> mounts the folder as res:// and then every *.wpak in <folder>/data, by name (so patch.wpak goes over game.wpak), with the key from the environment, before it looks for packages. Reads are safe from several threads; a file is read, decrypted, decompressed and checked when it is asked for, a file that is neither compressed nor encrypted is streamed without being read whole (and without its hash checked).

    Encryption and the key¶

    If WEFT_PACK_KEY is set (64 hexadecimal digits: 32 bytes) the pack is encrypted; if it is not, it is not. No key is set up for your game: the repository has none, so packs are plain. (The continuous integration uses a public test key for its export test only, see Testing an export; never ship a game with it.) When you want one, put it in .env (which git ignores and the ./build.sh wrapper loads), make the same key available to everything that makes or opens packs (the editor, the tools, a CI secret), and never commit it or print it (a PackKey writes itself as PackKey(…)). A pack made with one key cannot be read with another, and changing the key means making the packs again.

    Where each program gets the key:

    • Development runs (--game <folder>, the editor, --pack, --export) read WEFT_PACK_KEY from the environment.
    • An exported game has it in its executable: --export encrypts the pack with the key it finds in the environment and writes the key, masked, into a reserved slot of the copy of the runtime (PackKeySlot; into every copy of it, when the compiler emitted the data more than once). The game reads the slot first and the environment after it, so it needs no variable (and a variable does not override the embedded key).

    The embedded key is obfuscation, not protection

    The slot keeps the key out of strings and out of a casual look at the file: the 32 bytes are XORed with a hash of a random salt and a constant, all of which are in the file next to them, and the format is documented here. Anyone who wants the key can read it from the executable or from the memory of the running game. Use a key for one game, and expect it to be found.

    What it does, in detail (PackFormat has the layout):

    • Each part has a random 32-byte salt; the key that seals a part is HKDF-SHA256(key, salt), so the pack key never encrypts anything directly and two packs of the same files differ.
    • Every file and the index is its own AES-256-GCM blob (nonce | tag | ciphertext, a random nonce each time). A wrong key, or a single changed byte, fails the check instead of producing garbage. The file's path is authenticated with it, so a file cannot be moved to another path in the pack.
    • The first four bytes of the pack are WPAK without a key, and with one a few bytes of a hash of the key: an encrypted pack has no signature to search for, and opening one with the wrong key, or with none, is an error that says so (without the key in it).
    • Compression comes first and encryption after it (encrypted data does not compress). Without a key, damage is found by the zstd checksum of a compressed file and by a hash (the first 16 bytes of the SHA-256 of the file) that is checked for every file read whole.

    AES-GCM comes from the platform: Windows and macOS have it, and on Linux it needs OpenSSL (libssl), which desktops and Steam's runtime have.

    What it is not. A game has to be able to open its own packs, so the key is in the game (the embedded slot above); a determined person can get it out. The encryption keeps the content from being taken apart casually and makes a changed pack fail to load. It is not copy protection.

    Tests¶

    Tests/Weft.Content.Tests: the key, a round trip of every kind of file (empty, text, noise, nested), compression only where it pays, mounting, streaming, encryption (the content and the magic are not in the file, a salt per pack, no key and a wrong key), tampering (a flipped byte in a file or the index of a sealed pack, in a stored and in a compressed file of a plain one, a truncated file, a part missing), split parts (also a file bigger than a part, and sealed), patch packs, path rules, and many threads reading at once. Tests/Weft.Runtime.Tests runs a game from a pack with a patch pack over it, and an encrypted game with the key from the environment. GamePackerTests covers the library: plain and cooked packs, sources dropped and artifacts kept, authored documents cooked at their paths and reading back equal to their source, UIDs surviving the dropped sidecars, excluded prefixes, nothing imported (an error, and not one when asked), a document that does not parse, patch packs over a cooked base, and an encrypted split pack.
