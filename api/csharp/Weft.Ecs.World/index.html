    Namespace: Weft.Ecs

    ApplyOverrides(Entity, IEnumerable<PrefabOverride>, PrefabApplyTarget)¶

    Makes what an instance changed part of its prefab: the overrides are written into the prefab's file (the ids of the file stay, an added entity takes the next id and a removed one is taken out), the file is read back and checked, and then every instance of the prefab follows it in place, this one included, which now has nothing to say about what was applied. It is all or nothing: when anything is refused, written wrongly or cannot be followed, the file is put back byte for byte and the instances are as they were.

    public PrefabUpdate? ApplyOverrides(Entity root, IEnumerable<PrefabOverride> overrides, PrefabApplyTarget target = PrefabApplyTarget.InstancePrefab)

    Parameters¶

    root Entity

    overrides IEnumerable<PrefabOverride>

    target PrefabApplyTarget

    Returns¶

    PrefabUpdate?

    What following the file did (every instance of every prefab written), or null when nothing was written.

    Remarks¶

    A file is rewritten as the engine writes prefabs (comments and layout of a hand-written file are not kept), by a write that leaves the old file whole when it is interrupted, and only when it is writable, is what the library has read (it is refused when it changed on the disk since: reload it first), and is not read-only. writes the one file the instance names; writes the file that defines each entity, which may be several. A file that something between the instance and it pins (the instance's prefab holds its own override of the same field) keeps overriding it: the override is still listed afterwards.

    What is written must stand on its own in a prefab: an Entity field has to name an entity of the same instance (it is refused when it names one outside, or one the instance added), and an added entity brings what is below it, its instances included, with fields that name nothing outside the prefab. Removing an entity takes it from the prefab for everyone: the changes other prefabs and scenes hold for it are kept aside and apply again if it comes back.

    Not undoable by Restore: it writes a file. A tool that offers undo writes the file back (see the commands of Weft.Host).

    Exceptions¶

    InvalidOperationException

    Something is refused: pending updates, a missing or changed file, an override that cannot stand in a prefab, an instance that cannot follow.

    UnauthorizedAccessException

    A file to write is read-only or in a source that cannot be written.

    ApplyPrefabUpdates()¶

    Makes every instance of a prefab that changed follow it, in place: the entities that are still in the prefab keep their ids (so a selection, a reference from elsewhere and a script's variable stay valid), what the instance changed is kept where its target still exists (a field set to another value stays that value; the rest follows the prefab), what the prefab gained is made, what it lost is destroyed, and what the instance changed on something the prefab lost is kept aside in the instance and comes back with it. An instance that cannot be updated (the new prefab nests too deep, expands to more than entities, something throws while it is changed…) is left exactly as it was and reported in . Nothing is lost: a scene saved after an update is what saving it before, changing the prefab and loading it would be.

    public PrefabUpdate? ApplyPrefabUpdates()

    Returns¶

    PrefabUpdate?

    What was done, or null when no prefab changed since the last call (or another call is running).

    Remarks¶

    Call it from the thread that owns the world, where entities may change (a frame boundary), after for every file that changed: one call is one update for all of them. It is not undoable; see for what an editor does about its history. What was made after the change was announced was made from the documents the instances were made from, and is brought up to date with them; an instance that was saved over its own prefab () already has what the file says.
